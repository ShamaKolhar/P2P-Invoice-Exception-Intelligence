# Business Requirements: P2P Exception Rules

Scope: automated detection of six exception types on purchase-order line
items ("cases") in the Procure-to-Pay process, computed from the BPI
Challenge 2019 SAP event log. Each rule below is implemented in
`src/p2p_exceptions.py` and documented in the "Rules" sheet of
`outputs/excel/P2P_Exception_Log.xlsx`.

## E1 - Invoice recorded before goods receipt (compliance breach)

**Given** a purchase order line item in the "3-way match, invoice after GR"
item category (where goods receipt must precede invoicing)
**When** the case's invoice receipt timestamp is earlier than its goods
receipt timestamp
**Then** the case is flagged E1, since this violates the required sequence
for that category.

## E2 - Price change after PO creation

**Given** a purchase order line item
**When** a "Change Price" event appears anywhere in its event history
**Then** the case is flagged E2, so a reviewer can confirm the final matched
value reflects the latest agreed price.

## E3 - Quantity change

**Given** a purchase order line item
**When** a "Change Quantity" event appears anywhere in its event history
**Then** the case is flagged E3, so a reviewer can confirm the matched
quantity is still correct.

## E4 - Payment block set

**Given** a purchase order line item
**When** a "Set Payment Block" or "Remove Payment Block" event appears in
its event history
**Then** the case is flagged E4, since a block indicates the case needed
manual intervention before payment could proceed.

## E5 - Invoice receipt cancelled or repeated

**Given** a purchase order line item
**When** more than one "Record Invoice Receipt" event exists for the case
**Then** the case is flagged E5, since this may indicate a duplicate or
corrected invoice submission that needs review before payment.

## E6 - Long cycle time

**Given** a purchase order line item with both a "Create Purchase Order
Item" and a "Clear Invoice" event
**When** its cycle time (days between the two events) exceeds the 90th
percentile of cycle times for its own item category
**Then** the case is flagged E6, since it is taking unusually long to clear
relative to similar items.

## Notes

- A rule is only computed if the activity names and case attributes it
  depends on are confirmed to exist in the loaded event log (see
  `outputs/rules_skipped.txt`, generated by `src/p2p_exceptions.py`).
- These six rules are a starting control set for this prototype, not an
  exhaustive AP exception framework.
